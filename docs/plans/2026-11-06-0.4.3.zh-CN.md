## 设计决策（2026-11-07 拷问确认）

### #30 打包

- **一个 `ScriptView`。** `script_view!()` 在 debug 读 `CARGO_MANIFEST_DIR/ui` 的文件（开了 `dev-reload` 就热重载），release 用构建时嵌入的副本；宿主只写一套挂载代码。要显式选时用 `ScriptView::files(path)` / `ScriptView::embedded(&UI)`。删掉 `FileScriptView` 和 `EmbeddedScriptView`，不留别名。
- **嵌入走 build.rs。** 新 crate `gpui-rhai-build`（不依赖 gpui）：`build.rs` 里调 `gpui_rhai_build::embed_ui("ui")`，写到 `OUT_DIR` 并声明 `rerun-if-changed`，改了 `ui/` 自动重新嵌入。
- **删掉 `gpui-rhai embed`。** `init` 改为生成 build.rs；再跑 `embed` 时报错并说明怎么迁移。
- **文件覆盖。** debug 下 `script_view!()` 认 `GPUI_RHAI_UI=<目录>`；release 默认不认，宿主显式调 `.ui_override_env("变量名")` 才认（变量名由宿主定，omt 可以继续用 `OMT_UI`）。理由：已签名的发布版若默认允许环境变量换脚本，等于给所有应用开了注入口。
- **`gpui-rhai bundle`。** 只做 macOS .app：生成 Info.plist，PNG 转 icns，默认 ad-hoc 签名，可选 `--sign <证书>`，不做公证。配置写在 Cargo.toml 的 `[package.metadata.gpui-rhai.bundle]`（名称、identifier、图标、额外的二进制和资源），命令行参数优先。
- **`gpui-rhai dev --bundle`。** 把 debug 二进制套进临时 .app 再启动，脚本照旧读源文件、热重载；用来在开发时测系统通知和 Dock 角标（macOS 只给有 identifier 的 bundle 发）。
- **首次发布。** crates.io 的 Trusted Publishing 不能新建 crate：发 0.4.3 时由维护者在打 tag 前手动 `cargo publish -p gpui-rhai-build` 一次，再在 crates.io 加它的 Trusted Publishing 配置；之后随发布流程走。

### #21 shot

- **由应用自己的 example 挂载。** gpui-rhai 提供 `gpui_rhai::offscreen`（开离屏窗口、等稳定、执行步骤、存 PNG）；应用的 `examples/shot.rs` 挂上自己的扩展，`init` 生成模板；`gpui-rhai shot ...` 运行这个 example 并透传参数。
- **`test-support`。** gpui-rhai 加 feature `offscreen-pre` / `offscreen-fast`（打开对应 fork 的 test-support），默认不开。实现时从单个 `offscreen` 改成按后端分开：单个 feature 只能写成弱依赖 `gpui?/test-support`，而 Cargo 会把弱依赖指向的另一个 fork 整族（gpui-fast-* 等）写进应用的 lockfile，`gpui-rhai check` 会误报「同时解析到 gpui-pre 和 gpui-fast」，omt 的 lockfile 也会多出 gpui-pre 一族。应用只在 `[dev-dependencies]` 打开，release 二进制里没有（resolver 2 分开 dev 的特性集）。主 workspace 的 lockfile 会多几个 test-support 依赖；发布检查清单的说法改为「默认特性和发布构建里都不打开」，CI 加一项检查。
- **步骤。** 常用的是命令行参数（`--theme --size --click <名称> --key <组合键> --wait <毫秒> --out`），按顺序执行；复杂流程用 `--steps 文件.jsonl`，沿用 automation 的 JSON-lines 协议，另加 `capture` 命令以便一次截多张。

### #28 系统文件拖放

- 脚本拿不透明句柄和展示信息：DropZone 回调收到 `#{ files: [#{ file, name, size, kind }] }`，`file` 是带类型的不透明句柄，`name` 是不含目录的文件名；脚本把 `file` 交给宿主的 capability，宿主用 `view.dropped_file_path(&handle)` 换回真实路径。安全边界（脚本拿不到文件系统路径）不变。
- 宿主按视图开启：`ScriptView::accept_file_drops(true)`，默认关；开了以后，声明 `payload_types: ["os.files"]` 的 DropZone 才响应。
- 文件夹也能拖，用 `kind: "file" | "dir"` 区分；DropZone 可用 `file_kinds: ["file"]` 限定。

## GPUI 升级（有条件）

一个二进制里只能有一份 gpui-fast。nsh-platform-gpui 目前最新是 0.4.0（2026-11-04），依赖 `gpui-fast ^0.1.9`，在 0.1.11 及以后编不过（`KeyBinding::new` 改为要 `'static`）。gpui-rhai 如果先升，omt 的单二进制就会断。

- 0.4.3 发布前 nsh 发布了基于 gpui-fast 0.1.13 的版本：本版升到 gpui-pre 0.3.11 + gpui-fast 0.1.13（MSRV 已是 1.99，满足它们要的 1.98）。
- 否则：在分支上备好适配，nsh 升级后的那个版本再发。已评估的工作量：`action.rs` 4 处（动态串 `Keystroke::parse`、`KeyBinding::load` 末参变为 `&App`），以及 16 条 `ScrollWheelEvent` / `on_scroll_wheel` 弃用警告。
- 版本约束：gpui-fast 0.1.13 依赖 gpui-pre 基础 crate `=0.3.11`，两者必须一起升。

gpui-fast 上的 cache island 和滚动层原生支持（列表改由 `ListState` 驱动，宿主不再需要 `GPUI_SCROLL_LAYERS=0`）跟在升级之后做，免得在 0.1.9 和 0.1.13 上各写一遍。
