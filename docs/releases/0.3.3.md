# gpui-rhai 0.3.3

Release date: 2026-10-29. A patch release, compatible with 0.3.2 in Rhai and
in Rust. Runtime API stays **3** and MSRV stays 1.95. gpui-pre/core/platform
move to **0.3.9**: a Host that depends on `gpui`/`gpui_platform` directly pins
`=0.3.9`. Upgrade core, registry and CLI together.

This release is about frame and commit cost. A frame replays the parts of a
view that did not change instead of building, laying out and painting them
again, and a commit does work in proportion to what changed. No Rhai source
changes; no registry module changes. The full list is in the
[CHANGELOG](../../CHANGELOG.md).

## Frame replay

A subtree of 16 nodes or more with nothing that changes from frame to frame is
embedded as a cached GPUI view (a cache island) and replayed while its nodes
and what it inherits stay the same. Motion, signal styles, scroll containers,
virtual collections, overlays and layers, primitives, canvases, images,
element refs, raw pointer handlers and window drag areas stay outside islands.
An island's parent is a flex column, its height follows its content and its
width must not depend on its content: the width of a window
(`ScriptApplication`, script windows) is known, a Host says so for a view it
mounts with **`ScriptViewConfig::host_sets_width(true)`**, and a row's one
growing child, as an `AppShell`'s main area, takes the room its fixed siblings
leave. A render of the whole view, as a state change in the view itself makes,
still replays the subtrees it renders the same.

Replay is on by default. `ScriptViewConfig::render_islands(false)` or
`GPUI_RHAI_RENDER_ISLANDS=off` renders every frame in full;
`GPUI_RHAI_RENDER_ISLANDS=verify` panics when a replayed subtree would lay out
at another height. See [Frame replay](../performance.md#frame-replay).

A wheel over a scrollbar and a drag that autoscrolls a collection now notify
the scrolling view instead of refreshing the window, so the window's islands
beside them replay.

## Commit cost

A subtree a commit shares with the last one keeps its retained nodes, which
are now shared, and the node table is copied rather than rebuilt. Motion, exit
ghosts, signal validation, resource budgets, collection bindings, page
visibility, semantics and the walks a view makes after a commit read counts the
retained tree keeps per subtree, or carry what they inherit down the tree,
instead of walking all of it or each node's ancestors. A geometry state a
transaction shares is copied only when a change needs it. Rendering a node
also does less: building a view of 4,100 nodes in full took 3.8 ms instead of
6.3 ms.

## Measured

Release build on an Apple Silicon Mac, p50 per step, against 0.3.2 with the
benchmark added (`benchmarks/baselines/`):

| Scenario | 0.3.2 | 0.3.3 |
|---|---:|---:|
| Scroll a 400-row Table above 1,000 plain rows, within rendered rows | 18.2 ms | 0.74 ms |
| The same, a step that renders new rows | 43.4 ms | 4.0 ms |
| Above 2,500 rows, within rendered rows | 49.5 ms | 1.2 ms |
| Above 2,500 rows, a step that renders new rows | 120.7 ms | 7.4 ms |

Typing into a field of an `AppShell` with a sidebar and three cards took
0.41 ms a keystroke with islands on and 1.8 ms with them off when the draft is
in a component around the field, and 1.1 against 2.5 ms when it is in the
view, which renders the view whole.

GPUI itself renders every cached view again on some frames: a pointer click
(its active state), a focus change and an inspector pick.

## Fixes

- `motion_hover` and `motion_press` run. On a node with no other pointer
  handling they never received the pointer events, and `motion_hover` on a
  node with its own handlers, such as `on_click`, made the render fail.
- Realizing items of a virtual collection inside a `motion_group` no longer
  copies every item it keeps and adds the group to component items again on
  every scroll; new items take the group, once.
- In an application with several script windows, a commit in one window no
  longer drops the virtual collection state of the others.
- A commit commits its runtime transaction before it publishes the new tree,
  and rolls the runtime and the engine back if that fails.

## Upgrading from 0.3.2

Pin a direct GPUI dependency to the new family; `gpui-rhai check` reports a
mismatch:

```toml
gpui = { package = "gpui-pre", version = "=0.3.9", default-features = false, features = ["font-kit"] }
gpui_platform = { package = "gpui-pre-platform", version = "=0.3.9", default-features = false, features = ["font-kit", "runtime_shaders", "wayland", "x11"] }
```

The APIs gpui-rhai uses did not change between 0.3.7 and 0.3.9; a Host's own
GPUI code may meet `Keystroke::parse` taking `&'static str`, `KeyBinding::load`
taking `&App`, and `ScrollWheelEvent` gaining `source`. In 0.3.9
`debug_selector` takes effect only in debug builds.

A Host that mounts a view filling its window or a pane it sizes adds
`.host_sets_width(true)` to the view's `ScriptViewConfig`. Tests that count
renders exactly may want `render_islands(false)`.

## Not in this release

An optional GPUI Fast backend was evaluated and is not shipped: gpui-rhai's
per-frame registries (overlays, interactions, presented geometry, virtual list
frames) are refilled by each view's prepaint, which GPUI Fast skips for the
views and list rows it retains.
